# Прогон по полётной математике PX4

Разбор C++ идёт не своим разборщиком, а через представление, которое выдаёт сам
компилятор. Шаблоны разворачивает clang, типы выводит clang, препроцессор
выполняет clang — нам остаётся арифметика. Поэтому `matrix::Vector3f` с
наследованием и перегрузкой `operator()` читается так же легко, как обычная
функция на C.

Проверено на [PX4/PX4-Matrix](https://github.com/PX4/PX4-Matrix) — той самой
библиотеке, которая считает на борту. Сборка: `clang++ -std=c++14 -O2
-ffp-contract=off`. Запрет слияния умножения со сложением обязателен: иначе
компилятор сольёт их в одну операцию, и граница будет посчитана не для той
программы.

Все числа ниже получены этими командами:

```
git clone --depth 1 https://github.com/PX4/PX4-Matrix.git
python tools/analyse_cpp.py your_file.cpp --range=-1e3..1e3 -I PX4-Matrix
```

## Две находки, обе проверены запуском

Не нашей моделью — скомпилированной программой на `-O2`.

### `Vector3f::norm()` возвращает ноль и бесконечность

```c++
Vector3f v(1e-25f, 1e-25f, 1e-25f);   v.norm()  ->  0        верно 1.732e-25
Vector3f v(1e20f,  1e20f,  1e20f);    v.norm()  ->  inf      верно 1.732e+20
```

Причина: `norm()` считает корень из суммы квадратов. Квадрат `1e-25` в одинарной
точности исчезает в ноль, квадрат `1e20` переполняется — задолго до того, как это
случилось бы с самим ответом. Через `hypotf` оба случая дают верный ответ.

### `Vector3f::normalized()` возвращает бесконечности на НЕнулевом векторе

```c++
Vector3f(1e-25f, 1e-25f, 1e-25f).normalized()  ->  (inf, inf, inf)
                                        верно  ->  (0.577, 0.577, 0.577)
Vector3f(0, 0, 0).normalized()                 ->  (nan, nan, nan)
```

Первый случай важнее второго. Вектор не нулевой, единичный вектор для него
существует и представим в формате точно — а функция отдаёт бесконечности, потому
что делит на норму, которая до этого исчезла в ноль. Автопилот получает `inf`
вместо направления.

Инструмент предупреждает об этом статически, до полёта:

```
ВНИМАНИЕ: / от sqrt(((a1*a1) + ((a0*a0) + (a2*a2)))) на [-9.88e-324, 1.73e+03]
          — делитель накрывает ноль, код вернёт inf или NaN
```

### `Eulerf(Quatf)` отдаёт NaN в тангаже на НОРМИРОВАННОМ кватернионе

Это самая серьёзная из трёх. В `matrix/Euler.hpp` написано:

```c++
theta() = asin(-dcm(2, 0));
```

Без обрезки аргумента. У настоящего кватерниона значение `-dcm(2,0)` по
математике не выходит за отрезок от минус единицы до единицы, но считается оно в
одинарной точности, и округление выталкивает его чуть за единицу. `asinf` от
такого аргумента возвращает NaN.

Живой пример, найденный перебором на той же сборке:

```
кватернион q = (0.691335618, 0.148509696, 0.691335559, -0.148509696)
его норма    = 1              (нормирован, q.normalize() уже применён)
-dcm(2,0)    = 1.00000012     (арксинус требует не больше 1)
Eulerf(q):     крен = 0.147078   тангаж = NaN   курс = -0.188221
```

Частота: из 2 000 000 кватернионов, построенных около тангажа 90 градусов,
**NaN получен в 925 180 случаях**. Это не редкий угол: вертикальная ориентация —
обычный режим для VTOL на переходе и для подвеса, смотрящего вниз.

Оговорка, чтобы счёт был честным: выборка нарочно сделана около 90 градусов. При
обычном тангаже этого не происходит. И я не проверял, известно ли это
разработчикам PX4 — утверждается только то, что проверено запуском.

Инструмент называет причину статически, до полёта:

```
ВНИМАНИЕ: asin от ((q1*q3 - q0*q2) * -2) на [-4.00e+00, 4.00e+00]
          — аргумент может выйти за отрезок от -1 до 1, и тогда код возвращает
          NaN. Это классический путь, которым угол ориентации становится NaN:
          значение математически внутри диапазона, но округление выталкивает его
          чуть за единицу.
```

Лечение в одну строку: обрезать аргумент перед арксинусом.

## Насколько туже становится граница

Диапазон каждого входа `±1e3` — обычные координаты и компоненты кватерниона.

| функция PX4 | граница как есть | после переписи | туже в |
|---|---:|---:|---:|
| `Quatf::norm()` | 5.595e-01 | 6.104e-05 | 9 167× |
| `(a - b).norm()` расстояние | 1.296e+00 | 1.221e-04 | 10 621× |
| `Vector3f::norm()` | 3.953e-01 | 6.104e-05 | 6 477× |
| `Quatf(Eulerf(r,p,y))` | 9.227e-05 | 1.192e-07 | 774× |
| `Dcmf(Quatf)` элемент | 3.125e-01 | 6.250e-02 | 5× |
| умножение кватернионов | 4.375e-01 | 1.250e-01 | 3× |

Предложение для первых трёх одно и то же: `hypot` вместо корня из суммы
квадратов. Для остальных — перестановка слагаемых и `fma`.

## Что прочитано и что нет

Из тринадцати функций расчётной поверхности прочитано **двенадцать**.

Арксинус и арккосинус теперь разбираются: у них производная на концах отрезка
бесконечна, поэтому рядом с единицей работает гёльдерова оценка
`|asin(x) - asin(y)| <= (pi/sqrt(2))*sqrt|x-y|`. Константа проверена численно на
шестистах тысячах пар, и на паре (-1, 1) она даёт равенство — то есть точная, а
не с запасом. Измеренная ошибка сверяется с границей отдельным тестом на точках,
прижатых к концам отрезка.

Не читается одна функция — крен через `atan2` с ветвлением по близости к
вертикали: там ветвление, а значение за ним зависит от того, чего мы не
моделируем.

Отвергается также всё, где после оптимизации в теле остались обращения к памяти,
циклы или ветвления: значение за ними зависит от того, чего мы не моделируем, и
притворяться, что моделируем, значило бы считать границу для другой программы.

## Почему представление компилятора — это лучше исходника, а не хуже

Обычное возражение: вы считаете не то, что я написал. Наоборот.

Без `-ffast-math` компилятор обязан сохранять смысл вещественных операций, а
`-ffp-contract=off` запрещает единственное преобразование, которое он иначе
сделал бы молча. Значит представление — честная запись той же программы, но уже
**с развёрнутыми шаблонами и подставленными вызовами**, то есть ровно то, что
исполнится на борту. Граница считается для исполняемого кода, а не для его
исходного вида.

Побочно это открывает всё, что компилирует LLVM: C, C++, Rust, Swift.
